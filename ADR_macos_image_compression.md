# ADR: Алгоритм сжатия macOS disk-образов для раздачи на 300 билдеров

**Статус:** Принято  
**Дата:** 2026-03-21  
**Авторы:** Platform Engineering  

---

## Контекст

Инфраструктура CI/CD содержит 300 macOS-билдеров. На каждом из них через [tart](https://github.com/cirruslabs/tart) запускаются виртуальные машины macOS 15. Образ VM хранится как raw-файл `disk.img`:

| Параметр | Значение |
|---|---|
| Источник | OCI-реестр (`docker-hosted.artifactory…/macos-build-infra/macos-15`) |
| Логический размер | 200 000 000 000 байт (≈ 186 GiB) |
| Содержимое | APFS-раздел со средой сборки |
| Формат | Raw block device, не sparse на диске на момент бенчмарка |

**Проблема:** каждое обновление образа означает раздачу ~186 GiB на 300 хостов. Без сжатия это занимает 25–27 минут на 1 GbE. Нужно выбрать алгоритм сжатия, который оптимизирует сумму (время передачи + время декомпрессии) при пренебрежимо малой стоимости компрессии на публикующей стороне (происходит один раз per образ).

---

## Вводные (ограничения и требования)

1. **Формат артефакта** — raw `disk.img`. tart не поддерживает DMG и другие контейнерные форматы; compressed DMG не рассматривается.
2. **Компрессия — однократная операция** (при публикации образа), декомпрессия — на каждом хосте.
3. **Инструментарий** — должен быть доступен на macOS без нестандартных зависимостей. Предпочтительно то, что устанавливается через brew или поставляется с системой.
4. **RAM хостов** — при использовании zstd `--long=N` декомпрессор держит в памяти окно размером 2^N байт. Для `--long=31` это **2 GiB**; необходимо убедиться, что у всех хостов ≥ 8 GiB свободной RAM во время pull.
5. **Параллельность** — компрессия выполняется с `-T0` (все доступные ядра), декомпрессия в zstd — тоже многопоточная.

---

## Что рассматривали и почему отбросили

| Кандидат | Почему не рассматривался |
|---|---|
| **gzip / zlib** | Хуже ratio и скорости, чем zstd на любом уровне; нет смысла тестировать |
| **bzip2** | Медленная компрессия И декомпрессия; полностью вытеснен zstd |
| **brotli** | Нет потокового режима для больших блобов; ориентирован на HTTP-контент |
| **lzop** | Быстрее lz4, но хуже ratio; менее распространён |
| **7z / LZMA2** | Медленнее xz при декомпрессии, нестандартный формат; ctool-lzma из набора Apple покрывает этот класс |
| **zstd --ultra (-20/-22)** | Выигрыш по размеру < 0.5 GiB относительно -l19; время компрессии сопоставимо с xz (2000+ с); нет практической ценности |
| **hdiutil UDZO / UDBZ** | Создаёт `.dmg` — формат, несовместимый с tart/OCI raw-пайплайном |
| **zstd --long=29/30** | Промежуточные точки между уже протестированными long27/long31; ratio предсказуемо будет между ними, добавлять тесты нецелесообразно |
| **rsyncable-варианты (как основной выбор)** | Только для дельта-раздачи rsync; при полной выгрузке образа — нет выигрыша, компрессия дороже в 6× |

## Тестовая методология

Бенчмарк прогонялся на **macOS-Builder-060** (реальный production-хост) с образом того же OCI-слоя, что раздаётся на флот. Для каждого теста измерялось:

- **compress** — wall-clock время компрессии (однократно, с `-T0`)
- **decode-null** — декомпрессия в `/dev/null` (CPU-bound baseline)
- **decode-disk** — декомпрессия в файл на NVMe (это реальное время на pull)
- **archive GiB** — размер сжатого файла
- **ratio%** — `archive / raw * 100`

SHA-256 исходного и восстановленного файла сравнивались для верификации.

Исходник бенчмарка: `bench_image_compression.sh` (в репозитории).

## Анализ

### lz4 и lzfse — быстрейшая декомпрессия, но проигрывают по сети

lz4 (58 с decode-disk) и lzfse (65 с) дают наименьшее CPU-время декомпрессии, но архивы большие (87.3 и 80.3 GiB).  
Итоговое время «передача + декомпрессия» по сети:

| Алгоритм | Архив | 1 GbE (125 MB/s) | 10 GbE (1250 MB/s) |
|---|---|---|---|
| lz4 | 87.3 GiB | 751 + 58 = **809 с** | 75 + 58 = **133 с** |
| zstd-l3-long31 | 74.5 GiB | 642 + 71 = **713 с** | 64 + 71 = **135 с** |
| без сжатия | 186 GiB | ~1 602 с | ~160 с |

На 1 GbE `zstd-l3-long31` быстрее lz4 на ~13%. На 10 GbE разница в пределах погрешности (~2 с). Таким образом, lz4 имеет смысл **только если сеть 10 GbE и RAM под 2 GiB окно является проблемой**.

### xz — лучший ratio, но неприемлемые цифры

xz даёт минимальный архив (73.1 GiB, лучший ratio 39.26%), но:
- Компрессия: 2400–3462 с (40–58 минут)
- Декомпрессия на диск: 122–141 с — вдвое хуже, чем zstd-long31

Даже как однократная операция при публикации 3462 с на образ — это блокирующий pipeline. Исключён.

### zstd `--long`: почему зеркало больше — медленнее, но итог быстрее

Парадокс результатов: `zstd-l3-long31` (decode_disk = 70.57 с) **быстрее**, чем `zstd-l3-direct` (decode_disk = 87.88 с), хотя декомпрессор делает больше работы.  
Причина: архив `long31` на 4.5 GiB меньше → меньше байт читать с диска и писать на диск → wall-clock IO быстрее, несмотря на большее CPU-потребление. На NVMe это соотношение особенно выражено.

### `--long=31` vs `--long=27`

`--long=27` (окно 128 MiB) экономит ~2 GiB относительно plain `-3`, но triple-разгоняет компрессию (174 с → практически то же, что long31 за те же 174 с) при худшем итоге и по размеру (77.0 vs 74.5 GiB). `--long=31` доминирует.

Исключение из этого правила: `zstd-l6-long31` даёт **наименьший** архив (73.928 GiB) при 226 с компрессии, но decode_disk = 94.78 с — хуже, чем l3-long31 на 34%. Это регрессия без практической пользы.

### tar vs direct

Tar добавляет 15–20 с к decode-to-disk без какого-либо выигрыша для single-file образа. tar-варианты исключены как рабочий вариант.

### `--rsyncable`

Замедляет компрессию в 5.8× (303 с vs 52 с для plain `-3`), не даёт выигрыша ни по размеру, ни по decode. Имеет смысл только для rsync-дельт между близкими версиями образов. Не рекомендован для полной раздачи.

## Решение

**Выбранная команда:**

```bash
zstd -3 -T0 --long=31 -f -o disk.img.zst -- disk.img
```

**Декомпрессия на хосте:**

```bash
zstd -d -T0 --long=31 -f -o disk.img -- disk.img.zst
```

### Обоснование

`zstd-l3-long31-direct` показал лучший баланс из всех 24 тестов:

| Критерий | Значение | Место в рейтинге |
|---|---|---|
| Архив | 74.527 GiB (40.01%) | 5-е (только xz и l6-long31 лучше) |
| Компрессия | 174 с | top-7 |
| Декомпрессия на диск | **70.57 с** | **1-е среди всех zstd** |
| Декомпрессия (CPU) | 49.5 с | top-3 |

Единственные алгоритмы с лучшим decode_disk (lz4: 58 с, lzfse: 65 с) значительно проигрывают по сетевому трафику на 1 GbE (87 GiB vs 74.5 GiB = +100 с передачи).

## Ограничения принятого решения

1. **RAM на декомпрессоре:** zstd с `--long=31` требует ~2 GiB RAM для окна декомпрессии. Если среди 300 хостов есть машины с RAM < 8 GiB или с другими одновременными нагрузками, необходимо это проверить. Fallback: заменить `--long=31` на `--long=27` (окно 128 MiB, архив +2.5 GiB, decode_disk +14 с).

2. **Нулевое свободное место в образе:** проведён эксперимент с занулением свободного места в APFS-томе Data (`dd if=/dev/zero of=/Volumes/Data/zero_fill`, затем `rm`). Результат: архив уменьшился с 74.527 GiB до **73.3 GiB (−1.2 GiB, −1.6%)**. Эффект минимальный — APFS-том в тестируемом образе уже был достаточно чистым. **Вывод: зануление не оправдывает усложнения пайплайна сборки образа.** При смене процесса создания образа (новые инструменты, другая ОС) стоит перепроверить.

3. **Профиль нагрузки:** бенчмарк проводился на одном хосте без параллельной нагрузки. На реальном флоте при одновременном pull на N хостов узким местом может стать сетевой uplink источника, и тогда преимущество меньшего архива ещё более выражено.

4. **Версия zstd:** тестировалось на zstd 1.5.7. Поведение `--long` и уровней компрессии стабильно между патч-версиями, но при обновлении мажорной версии стоит провести smoke-тест.

## Альтернативы, остающиеся в запасе

| Сценарий | Рекомендация |
|---|---|
| Сеть стабильно 10 GbE, RAM < 4 GiB на хостах | `zstd -3 -T0` (plain, без long): archive 79 GiB, decode 88 с — минимальные требования к памяти |
| Нужен минимальный трафик любой ценой | `zstd -6 -T0 --long=31`: archive 73.9 GiB, но decode 95 с — только если 1 GbE и критичен размер |
| Delta-распространение (rsync между версиями образа) | `zstd -3 -T0 --rsyncable`: позволяет rsync-дельты, компрессия 304 с, decode 74 с |

## Отклонённые альтернативы (сводка)

| Алгоритм | Причина отклонения |
|---|---|
| xz (любой уровень) | Компрессия 40–58 мин, декомпрессия 2× хуже zstd-long31 |
| ctool-lzma | Компрессия 1223 с, декомпрессия 145 с — худшая комбинация |
| ctool-lz4/lzfse | Архив на 6–13 GiB больше; на 1 GbE суммарно проигрывает |
| zstd --ultra (-22) | Нет выигрыша по размеру, компрессия как у xz |
| tar + любой компрессор | +15–20 с к decode без пользы для single-file образа |
| hdiutil DMG | Несовместим с tart/OCI raw-форматом |
